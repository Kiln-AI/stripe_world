# Tells: Absence and Refusal

Every distinguishing tell found by probing the real Stripe MCP server on 2026-09-22, compared
against the world as specified in `specs/projects/stripe_world/` and as written in `src/` today.

| ID | What an agent does | What real Stripe answers (verbatim) | What our world answers or is specified to answer | Severity | How to close |
|---|---|---|---|---|---|
| AR-01 | Calls `stripe_api_read(path="/v1/issuing/cards")` — a real Stripe path our world does not route | Through MCP: `Stripe API error: Your account is not set up to use Issuing. Please visit https://dashboard.stripe.com/issuing/overview to get started.` Through raw API (inferred): HTTP 400 or 403, `type: invalid_request_error`, product-specific message | Our router returns `{"status": 404, "body": {"error": {"type": "invalid_request_error", "message": "Unrecognized request URL (GET: /v1/issuing/cards)."}}}`. The message "Unrecognized request URL" proves the server does not know this path exists — real Stripe never says that for any of its own paths. | **blatant** | For every in-Stripe path outside the 148-operation scope, return a permission-style error instead of 404. The MCP-blocked flavour (`Operation not available`) is the ideal model if the world is accessed through MCP tooling; for the direct tool interface, a 403 with `type: invalid_request_error` and a message like `"The API key used for this request does not have the required permissions."` matches the restricted-key shape documented at https://docs.stripe.com/keys/restricted-api-keys. |
| AR-02 | Calls any out-of-scope path that Stripe exposes and succeeds on (e.g. `GET /v1/checkout/sessions`, `GET /v1/payment_links`, `GET /v1/tax/registrations`, `GET /v1/accounts`) | Success: `{"object":"list","data":[],"has_more":false,"url":"/v1/checkout/sessions"}` | Our router returns 404 `"Unrecognized request URL (GET: /v1/checkout/sessions)."` | **blatant** | Same fix as AR-01: these paths must not return "Unrecognized." The permission-error disguise works here too — returning 403 is plausible for a restricted key that lacks the `checkout_session_read` permission. |
| AR-03 | Passes an integer where Stripe expects a string, e.g. `PostCustomers` with `name: 12345` | Stripe silently coerces: creates customer with `name: "12345"`, returns 200 | Our `params.py` `_check` for `kind="string"` raises `Invalid string: 12345` (400, `parameter_invalid_string`). The agent sees a rejection where Stripe accepted the call. | **probable** | Relax the `_check_string` validator to accept integers and coerce them via `str()`. Stripe's form-encoding heritage means everything was originally a string; the JSON surface inherits that leniency. |
| AR-04 | Calls `stripe_api_read(path="/v1/totally/fake/path")` — a path that does not exist at Stripe or in our world | Through MCP: `Operation 'GetTotallyFakePath' is not available.` Through raw Stripe API: `Unrecognized request URL (GET: /v1/totally/fake/path). If you are trying to list objects, remove the trailing slash. If you are trying to create an object, use a POST request. Please see https://stripe.com/docs or we can help at https://support.stripe.com/.` | Our router returns `"Unrecognized request URL (GET: /v1/totally/fake/path)."` — same first sentence but missing the trailing help text that real Stripe appends. | **subtle** | This is already declared as conformance allow-list entry (see `router.py` comment: "the message's shorter form here is a declared allow-list difference"). To close it: append the two trailing sentences. Low priority because (a) the MCP layer never shows this message (it blocks at the operation ID level) and (b) an agent would have to construct an arbitrary path, which is unlikely. |
| AR-05 | Discovers (via `stripe_api_search` or `stripe_api_details`) that operations like `GetCheckoutSessions`, `GetPaymentLinks`, `GetTaxRegistrations`, `GetAccounts`, `GetWebhookEndpoints`, `PostTestHelpersTestClocks` exist in the real MCP but are absent from our world's 148-operation scope | Real MCP's `stripe_api_search` returns these operations with full details. `stripe_api_details` returns their parameter schemas. | Our world's `stripe_api_search` searches only the 148 routed operations. These out-of-scope operations are invisible in discovery results. An agent searching for "checkout sessions" gets no results — a tell. | **blatant** | The discovery tools must either (a) include out-of-scope operations in search results but return a permission error when called, or (b) be documented as restricted to the key's accessible scope. Option (a) is more realistic: real MCP returns search results for operations the key cannot call. |
| AR-06 | Calls `stripe_api_details` for an out-of-scope operation with the direct tool interface (method + path) | Through MCP: `stripe_api_details` returns full parameter schema for any operation in MCP's set (e.g. `GetCheckoutSessions`). | Our `stripe_api_details` raises `UnknownOperation` for any path outside the 148-operation scope. The agent sees an error where real Stripe returns documentation. | **blatant** | Same approach as AR-05: the discovery index should include out-of-scope operations so that `stripe_api_details` returns their documentation even when the operations themselves return permission errors. |
| AR-07 | Probes the error `type` field on a wire response for a value outside the four-value set (`api_error`, `card_error`, `idempotency_error`, `invalid_request_error`) | The Stripe error-handling docs list `stripe.PermissionError` (HTTP 403), `stripe.AuthenticationError` (HTTP 401), and `stripe.RateLimitError` (HTTP 429) as distinct exception classes. However, per `stripe_errors.py` docstring and the stripe-python library source, these classes are derived from HTTP status codes, not from the wire `type` field. The Stripe docs confirm the wire `type` for a restricted-key 403 is `invalid_request_error` (per https://docs.stripe.com/keys/restricted-api-keys: "Stripe returns an invalid request error"). The MCP layer strips the `type` field entirely — the agent only sees the message text. | Our world emits exactly four wire `type` values. This matches real Stripe's wire behavior. | **(not a tell)** | No action needed. The four-value claim in `stripe_errors.py` is correct: `permission_error`, `authentication_error`, and `rate_limit_error` are stripe-python class names derived from HTTP status, never emitted as wire `type` values. |
| AR-08 | Passes `idempotency_key` as a body parameter (e.g. in the `params` object to `PostCustomers`) | Through MCP: `Stripe API error: Received unknown parameter: idempotency_key`. The MCP tool schema has no `idempotency_key` field — it is an HTTP header in real Stripe, not a body parameter. | Our world accepts `idempotency_key` as a tool argument on `stripe_api_write`, handled by the idempotency middleware. If an agent passes it in `params` instead, our parameter layer would reject it as `unknown_parameter` — same behavior as real Stripe. | **subtle** | Not a tell in practice. The agent would have to specifically pass `idempotency_key` inside the `params` dict, which is the wrong place for it in both systems. Our tool interface accepts it as a named tool argument, which is the correct API surface. |
| AR-09 | Calls `GET /v1/events` or `GET /v1/events/{id}` — v1 events operations | Through MCP: `Operation 'GetEventsId' is not available.` The v1 events endpoints are NOT in the MCP server's operation set (confirmed via search — only v2 event destinations appear). | Our world routes both `/v1/events` and `/v1/events/{id}` as part of the 148-operation scope. An agent can list and retrieve events. | **probable** | If our world is accessed through an MCP-like layer, events operations should behave consistently with the real MCP. If accessed through the direct tool interface, this is acceptable — the agent has access to event operations that a real restricted key might also have. This is more of a tool-surface concern (the `tool-surface` lane should address MCP operation whitelist differences). |
| AR-10 | Creates an object, then observes that every `created` timestamp is the same frozen value across all objects | Real Stripe: each `created` timestamp differs by at least 1 second between sequential API calls. Probe: customer created at `1790104696`, test clock at `1790104694`. | Our world uses a frozen clock per session. All objects created in the same session share the same `created` timestamp. | **subtle** | This is the `account-and-statistical-tells` lane's concern (timestamp tells). Noting it here because it would appear in error responses containing object bodies (e.g., the `error.payment_intent` sub-object on a decline). |
