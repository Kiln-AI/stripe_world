# Envelope and Cross-Cutting: Tells

Every distinguishing tell found by probing the real Stripe MCP server against
our world's specified/implemented behavior, ordered by severity.

| ID | What an agent does | What real Stripe MCP answers | What our world answers (or is specified to answer) | Severity | How to close |
|---|---|---|---|---|---|
| EC-01 | Any successful `stripe_api_read` or `stripe_api_write` call | Bare JSON body: the API object or list envelope directly (e.g. `{"object":"list","data":[...],"has_more":true,"url":"/v1/customers"}` or `{"id":"cus_...","object":"customer",...}`) | ~~`{status, body, headers}` wrapper~~ **closed** (Phase 4): MCP tools return bare body on 2xx. | ~~blatant~~ **closed** | Remove the `{status, body, headers}` wrapper from `dispatch/response.py`'s `render()` and `middleware/stripe_envelope.py`. Return the bare body on success. |
| EC-02 | Any call that triggers a Stripe API error (400, 404, 402, etc.) | MCP tool error with a plain string: `"Stripe API error: <message>\n\nUse stripe_api_details..."`. No HTTP status code, no structured `{error: {type, code, param, ...}}` body visible. | ~~Successful tool return~~ **closed** (Phase 4): MCP tools raise `StripeToolError` with message `Stripe API error: <message>`. | ~~blatant~~ **closed** | Raise a Seahaven `ToolError` (or equivalent MCP error) whose text is `"Stripe API error: <message>"`. Drop the structured error body, the status code, and the headers from the agent-visible surface. |
| EC-03 | Passes `idempotency_key` as a parameter on a write call | `"Stripe API error: Received unknown parameter: idempotency_key"` — the real MCP has no idempotency support at all (it is an HTTP header, and MCP has no header mechanism) | Accepts `idempotency_key` as a tool parameter, implements full replay/mismatch/in-flight semantics | **blatant** | Remove `idempotency_key` from the tool's accepted parameters. Disable or hide the idempotency middleware. (Alternatively, accept the divergence as a deliberate feature for eval purposes and document it.) |
| EC-04 | Reads the `headers` key from a response | Always present in our world: `{"Stripe-Version": "...", "Request-Id": "req_...", "Idempotency-Key": "..."}` | ~~Headers visible~~ **closed** (Phase 4): MCP tools return bare body (no headers). `call_stripe` (raw face) still exposes headers for conformance testing. | ~~blatant~~ **closed** | Drop the `headers` key from the response envelope entirely. |
| EC-05 | Observes the error text suffix on a Stripe error | Real MCP appends: `"\n\nUse stripe_api_details with stripe_api_operation_id: \"...\" to see all required and optional parameters."` | Our world's error messages carry no MCP-layer help suffix. | **probable** | Append the MCP help suffix to every error ToolError message. Requires knowing the operation ID that was called. |
| EC-06 | Sends `limit=0` or `limit=-1` on a list endpoint | Returns a valid response with 1 item and `has_more: true` (silently clamped to 1) | Raises 400 `parameter_invalid_integer` with `param: "limit"` | **probable** | Clamp `limit` to `max(1, min(limit, 100))` silently instead of raising an error. |
| EC-07 | Sends `limit=101` or `limit=200` on a list endpoint | Returns a valid response with 100 items (silently clamped to 100) | Raises 400 `parameter_invalid_integer` with `param: "limit"` | **probable** | Same clamping as EC-06. |
| EC-08 | Reads `openapi_spec_version` from `stripe_api_search` or `stripe_api_details` results | `"2026-08-26.preview"` | Our world pins `"2026-08-26.dahlia"` in `stripe_envelope.py` | **probable** | Update `API_VERSION` to `"2026-08-26.preview"`, or match whatever the real server returns. (This is also a discovery-tools concern.) |
| EC-09 | Creates a customer and expands a deleted customer reference on a payment intent | Deleted customer stub includes `cache_context_key` field: `{"id":"cus_...","object":"customer","cache_context_key":"acct_...","deleted":true}` | Our world's deleted stub is `{"id":"...","object":"customer","deleted":true}` — three keys, no `cache_context_key` | **subtle** | Add `cache_context_key` to the deleted stub serializer if the real API always includes it. (Borderline — may be an object-shape concern for the other lane.) |
| EC-10 | Observes field ordering in a successful response | Real MCP returns fields in a specific order (e.g. customer: id, object, address, balance, created, currency, ...) | Our world's JSON serialization may produce different field ordering depending on `_json.dumps` settings | **subtle** | Ensure `_json.dumps` produces the same field order as the real API. (JSON field order is not semantically meaningful, but an agent doing string comparison would notice.) |
